# Supabase 注册、登录与订阅流程设计

## 目标

建立 Edward 的安全账号、试用、订阅和推荐奖励体系。Supabase Auth 管理身份认证；Edge Functions 处理试用资格、订阅状态、推荐奖励和抵扣；客户端永远不能自行声明已订阅、修改价格或发放奖励。

## 固定规则

- 注册支持邮箱和账号名；账号名全局唯一、不区分大小写，长度 3–32 个字符，仅允许中文、字母、数字、下划线和短横线。
- 密码只存储在 Supabase Auth，应用数据库不保存密码。
- 邮箱验证完成后才获得试用资格。
- 免费试用默认 3 天，可由后台调整为 0 天至任意天数；不要求绑定支付方式，不自动扣款。
- 每个账号只能获得一次试用；设备和 IP 风险控制阻止批量注册重复试用。
- 套餐价格、币种、折扣、试用天数、连续订阅规则和推荐奖励金额全部存储在 Supabase，可后台调整。
- 套餐折扣先计算，推荐抵扣后计算；抵扣不超过应付金额，余额可留到后续续订，不可提现或转赠。
- 推荐用户完成邮箱验证后，任意一次成功订阅付款都会触发奖励，不限连续订阅。
- 推荐奖励发放后 12 个月有效；退款、拒付或风控命中时冻结/撤销。
- 连续订阅关闭只影响下一周期；当前周期继续有效且不退款。

## 组件与数据模型

### `profiles`

`user_id`（关联 `auth.users`）、`username_normalized`（唯一）、`username_display`、`referral_code`（唯一）、`referred_by_user_id`、`created_at`、`updated_at`、`risk_status`。

账号名只通过服务端函数查找，不开放用户目录查询。推荐关系只能在注册时建立一次，禁止修改为其他推荐人。

### `subscription_plans`

`id`、`plan_key`、`name`、`currency`、`unit_amount`、`billing_interval`、`is_recurring`、`trial_days`、`discount_config`、`required_entitlement`、`status`、`effective_from`、`effective_to`、`created_at`、`updated_at`。

价格使用整数最小货币单位。新订单读取创建时的价格快照；后台修改价格不追溯已创建订单。

### `subscription_rules`

保存全局可调整规则：默认试用天数、推荐奖励金额、奖励有效期、注册/登录频率限制、设备风险窗口、抵扣上限和离线宽限期。规则按版本生效，订单和奖励保存使用的规则版本。

### `subscriptions`

`id`、`user_id`、`plan_id`、`status`（trialing/active/past_due/canceled/expired/revoked）、`current_period_start`、`current_period_end`、`cancel_at_period_end`、`provider`、`provider_subscription_id`、`created_at`、`updated_at`。

### `orders`

保存订单金额快照：原价、套餐折扣、推荐抵扣、实付金额、币种、规则版本、支付提供方状态和幂等键。客户端不可写入金额和状态。

### `referrals` 与 `credit_ledger`

`referrals` 保存推荐人、被推荐人、验证时间、首次/任意成功付款时间、奖励状态和风控结果；`credit_ledger` 使用不可变账本记录发放、使用、冻结、撤销和过期，余额由服务端聚合，不接受客户端直接更新。

### `trial_grants` 与 `risk_events`

`trial_grants` 保存一次性试用授予及规则版本；`risk_events` 保存注册、登录、设备/IP 哈希、失败次数、封禁窗口和触发规则。原始 IP 不写入业务表，使用带密钥的不可逆哈希并设置保留期。

## 认证流程

1. 客户端提交邮箱/账号名、密码、推荐码和设备证明到 Edge Function。
2. 函数先做格式校验、频率限制、风险检查，再调用 Supabase Auth 注册或登录。
3. 注册时创建唯一 `profiles`，原子写入推荐关系和试用资格；任一步失败整体回滚。
4. 邮箱验证成功后，服务端才将试用状态设为 `trialing`。
5. 登录返回短期 access token 和轮换 refresh token；客户端只保存会话，不保存密码。
6. 账号名登录先由服务端解析为用户邮箱/用户 ID，客户端不得读取用户目录。

## 订阅与授权流程

- 客户端请求套餐目录时只获得当前生效套餐和展示价格。
- 创建订单时服务端重新读取套餐与规则，生成价格快照并返回支付平台所需参数。
- 支付回调必须验签、幂等处理并更新订单、订阅和权益；客户端回调参数不可信。
- 任意资源目录、详情、预览、下载和组件写入请求都必须验证 JWT、订阅状态、有效期、资源要求和版本兼容性。
- 试用、订阅和权益均按服务端时间判断；本地缓存仅允许短期离线宽限，不能延长到期时间。

## 折扣与推荐奖励

计算顺序固定为：`原价 → 套餐折扣 → 推荐抵扣 → 应付金额`。所有金额使用整数运算并保存订单快照。

被推荐用户完成邮箱验证后，任意一次成功订阅付款触发一次奖励。退款、拒付、取消支付或风控命中时，奖励进入冻结状态；确认结算后才可使用。奖励有效期默认 12 个月，可由 `subscription_rules` 调整。

## 反滥用与防绕过

- Supabase Auth 开启邮箱验证、刷新令牌轮换和密码强度要求。
- 注册、登录、刷新令牌、推荐绑定和订单创建使用 IP、账号、设备风险窗口限流；连续失败采用指数退避和短时封禁。
- 推荐奖励要求邮箱验证和成功付款，推荐关系、奖励和账本均由服务端事务写入；同一设备、支付指纹、邮箱域名和异常推荐图谱进入风控队列。
- 不信任客户端价格、套餐、试用开始时间、系统时间、授权状态或推荐参数。
- 私有 Storage 只返回短时签名 URL；资源包和预览不使用公开 URL。
- 关键 Edge Functions 使用审计日志、幂等键和请求关联 ID；日志禁止密码、令牌和完整支付信息。
- 本地缓存按组件 ID、版本和内容哈希绑定授权；缓存不能生成新签名 URL，订阅到期后禁止新授权。

## 后台调整

后台管道只能由受控管理员调用，使用 service role key；普通客户端无管理写权限。价格、折扣、试用天数和奖励金额采用版本化配置，变更记录操作者、时间、原因和生效区间。

## 支付平台预留

当前不绑定支付平台。`orders`、`subscriptions` 和回调处理器使用 `provider` 抽象，未来接入支付平台时只增加验签适配器，不改变权益、折扣、推荐和授权核心规则。

## 验收标准

- 未验证邮箱不能获得试用或访问受限资源。
- 同一账号、设备或风险 IP 无法重复领取试用。
- 客户端篡改价格、套餐、试用日期、奖励或订阅状态均被服务端拒绝。
- 推荐奖励只在邮箱验证和成功付款后发放一次，退款/拒付可撤销。
- 关闭连续订阅只影响下一周期，当前周期不退款。
- 价格和规则后台修改后，新订单使用新版本，历史订单保持快照。
- 匿名请求、过期权益和伪造资源 ID 均不能取得资源签名 URL。
