# 汇付 Deno 支付适配与连续订阅设计

日期：2026-09-13  
状态：待用户审阅

## 目标

在不增加独立服务器的前提下，将 Edward 的支付后端固定在 Supabase Edge Functions，按汇付官方 Go SDK 的报文合同复刻当前所需能力：微信正扫、支付宝正扫、订单状态处理、异步通知和连续订阅。

## 已确认的 SDK 合同

汇付 Go SDK 的统一 POST 流程为：

1. 删除空值字段；
2. 将 `extend_infos` 展平到业务数据对象；
3. 对业务数据对象进行 JSON 序列化，并只替换 `<`、`>`、`&` 的 Unicode 转义；
4. 使用商户私钥进行 RSA PKCS#1 v1.5 + SHA-256 签名；
5. 发送外层对象：

```json
{
  "sys_id": "...",
  "product_id": "...",
  "sign": "...",
  "data": {"...": "..."}
}
```

当前实现把业务字段放在外层，并对排序后的 `key=value` 字符串签名，和 Go SDK 不一致，这是当前 HTTP 500 的首要修正点。

响应按 `{sign, data}` 解包；验签内容是响应中 `data` 的原始 JSON 文本，而不是重新排序后的键值字符串。所有请求和响应必须保留 HTTP 状态码、响应正文、请求流水号和汇付业务码。

## 支付渠道

支付创建统一使用汇付 `jspay` 适配器，业务层只传渠道和订单数据：

- 微信正扫：`trade_type = T_NATIVE`；
- 支付宝正扫：`trade_type = A_NATIVE`。

具体渠道扩展字段只允许来自官方文档和调试接口的已确认字段。不能把微信专用字段传给支付宝，也不能把前端 Checkout JS SDK 当作服务端签名替代品。

创建成功后从解包后的 `data` 读取二维码/支付链接字段；若业务码失败、响应为空、HTTP 非 2xx、验签失败或缺少二维码字段，统一写入可诊断的失败记录，不向客户端返回模糊的 `payment_unavailable`。

## 连续订阅

连续订阅不是客户端定时扣款，而是用户首次明确授权后由服务端执行周期扣款：

1. 创建订阅订单并记录套餐、折扣、金额、规则版本和幂等键；
2. 调用汇付协议/代扣授权流程，用户完成授权；
3. 保存汇付返回的绑定标识，不保存银行卡号、身份证号或短信信息；
4. 使用 Supabase 定时任务触发到期续订；
5. 每次续订使用新的请求流水号和幂等键；
6. 通过汇付异步通知或主动查询确认最终状态；
7. 退订只影响下一周期，当期不退款；
8. 失败重试必须有次数上限、退避和最终人工/用户处理状态。

Go SDK 中已确认的相关接口族包括 `quickbuckle/apply`、`quickbuckle/confirm`、绑定查询/解绑，以及 `trade/onlinepayment/withholdpay`。最终使用哪个授权组合，必须以当前商户已开通的汇付产品和官方调试接口字段为准；未确认的接口不进入生产实现。

## Supabase 组件

- `_shared/huifu.ts`：Deno 版公共 SDK 核心、RSA 签名/验签、报文封装、HTTP 诊断；
- `huifu-native-create`：微信/支付宝正扫创建；
- `huifu-order-query`：主动查询；
- `huifu-order-close`、退款接口：关闭和退款；
- `huifu-native-notify`：验签、幂等、订单状态更新；
- 订阅授权、订阅代扣、订阅查询/解绑 Edge Functions；
- Supabase 数据库保存订单、授权标识、订阅周期、规则版本和审计信息；
- Supabase Secrets 保存私钥、汇付公钥、系统标识和生产 API 地址。

客户端只能提交套餐/渠道选择和业务备注，金额、交易类型、分账、通知地址和密钥相关字段由服务端生成。

## 错误与安全

- 任何上游 HTTP 状态非 2xx 都记录 `upstream_status` 和截断后的 `upstream_body`；
- 空响应、非 JSON、业务失败码、签名失败分别使用独立错误码；
- 日志禁止输出私钥、完整签名、访问令牌和个人敏感信息；
- 所有创建和续订接口要求已认证用户；
- 数据库 RLS 阻止客户端修改订单金额、支付状态、授权标识和订阅到期时间；
- 通知接口不信任客户端身份，只接受汇付签名验证通过的通知，并使用订单幂等约束；
- 所有金额使用分为单位存储，禁止浮点累加；
- 续订任务必须验证订阅状态、当前周期、授权有效性和规则版本。

## 验收标准

1. Deno 生成的请求 JSON 与 Go SDK 的外层结构、`data` 序列化文本和签名算法一致；
2. 使用固定测试向量验证 RSA 签名和汇付响应验签；
3. 微信 `T_NATIVE` 与支付宝 `A_NATIVE` 均能生成可追踪的生产请求；
4. HTTP 500、空响应、业务码失败、验签失败均能在客户端显示可定位原因；
5. 异步通知重复投递不会重复记账或重复发放权益；
6. 连续订阅只在授权成功后执行，退订只影响下一周期；
7. Supabase Secrets、RLS、日志脱敏和金额边界检查通过；
8. 仅在官方文档和调试接口字段已确认后才允许生产调用。

## 未确认项

- 汇付当前生产环境对本商户开放的支付宝正扫具体扩展字段；
- 本商户连续订阅应使用的协议授权产品及对应必填字段；
- Supabase 项目当前是否已启用可执行的定时任务扩展。

这些项目在实现前必须通过官方文档、调试接口或商户后台确认，不能用猜测字段替代。
