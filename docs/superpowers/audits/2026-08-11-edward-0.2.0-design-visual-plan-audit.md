## 3. 阻塞项（P0）

### P0-1：声明 QtTest，却以 GoogleTest 语法编写首批测试

**状态：已修复（文档级）。** 新增 `docs/contracts/testing.md`，固定 QtTest + CTest；00–08 的测试示例已全部替换为 `void test...()`、`QCOMPARE`、`QVERIFY`。静态扫描确认计划中不再存在 `TEST(`、`EXPECT_*` 或 `ASSERT_*` 宏。

**证据：**

- 01 计划将技术栈写为 `Qt6/QtTest/QML`（`foundation-and-projects.md` 第 9 行）。
- 其首个测试使用 `TEST`、`EXPECT_EQ`（第 29–34 行）。02–08 也普遍使用 `TEST`、`EXPECT_*`、`ASSERT_*`。
- 环境指南没有安装或声明 GoogleTest；根 CMake 尚未存在，无法解释宏的来源。

**影响：** 阶段 01 的“先失败、后通过”无法被确定地运行；这不是编码细节，而是第一条构建与测试合同自相矛盾。

**必须修复：** 在实施前冻结一个 C++ 测试框架并逐份计划统一。建议采用 **QtTest + CTest**，因为计划已选择 Qt 6，不需要额外引入 GoogleTest：所有示例改为 `QTEST`、`QVERIFY`、`QCOMPARE`，并在 01 的 CMake 任务中给出测试目标、`add_test` 名称和标签。若坚持 GoogleTest，则必须在环境与 CMake 中锁定获取方式、版本、许可证与离线构建策略；不能两者混用。

### P0-2：实施计划尚不能一对一追溯全部已确认要求

**状态：已修复（文档级）。** 新增权威规格与追溯矩阵，覆盖 47 个 ARC/PRJ/CRT/TL/CMP/UI/RES/MOD/PLG/ACC/EXP 需求 ID；另新增逐文件视觉 route 基线。静态检查确认最终视觉清单 44 个 HTML 均存在，且 44/44 被 route 基线映射，无多余或缺失项。

**证据：**

- 视觉清单有 44 个最终 HTML 引用和多项不可变规则，但计划 05 仅提出泛化的 `VisualManifest` 路由测试（`workbench-resources.md` 第 38–50 行），没有列出每一页、每种选择状态、QML 路由、对象名、行为合同、截图基线及对应模块任务。
- 功能决定目前分散在约 1400 行操作台账、视觉清单和 9 份计划中；00 模块计划是“未来创建规格”，而不是现有的完整、可供后续任务引用的权威规格。
- 这会使实施者难以证明“每一条确认均被覆盖”，也容易把视觉状态实现成静态页面而缺少业务行为。

**影响：** 直接实施会出现选择性遗漏，尤其是首页/账户/资源升级/AI 状态/属性状态等视觉入口与引擎行为的连接处。

**必须修复：** 先新增一份 **0.2.0 权威规格与需求追溯矩阵**，每项至少包含：需求 ID、台账出处、视觉稿路径/状态、负责模块与任务、模型/接口、持久化位置、错误/离线状态、自动化验收编号。矩阵必须覆盖 44 个最终页面引用及全部全局视觉规则，然后才能开始模块 00。

### P0-3：跨平台依赖门不具备可复现性

**状态：已修复（文档级，待人工环境验证）。** 新增依赖锁定合同，固定依赖来源、tag、commit、前缀、pkg-config/CMake 发现方式、运行时内容与安装 smoke；开发环境指南已改为引用该合同。真实构建尚未运行，因为用户尚未按手动部署指南安装锁定依赖。

**证据：**

- 环境指南 macOS 命令仅安装 Homebrew 包，并以 `CMAKE_FIND_ROOT_PATH` 指向 FFmpeg/MLT（第 9–32 行）；没有说明计划中的 `cmake/Dependencies.cmake` 应如何从 pkg-config 解析 FFmpeg/MLT，或怎样验证 MLT 的 CMake/MLT++ 组件实际可用。
- Windows 仅要求“从 GPL 源码构建” FFmpeg 与 MLT（第 36–38 行），没有固定源码版本/提交、配置选项、补丁、构建命令、安装布局、DLL/plugin 部署规则与 CMake 查找契约。
- 计划 01 第 46 行又要求 CMake 直接发现 Qt、FFmpeg、MLT、JSON；当前指南不足以让两台机器得出同一结果。

**影响：** 同样的计划可能在 macOS 与 Windows 构建出不同能力、找不到依赖，或者到打包时缺少 MLT 插件/DLL。此问题直接违反稳定、兼容和跨平台优先原则。

**必须修复：** 在开始代码前补齐“依赖锁定与发现合同”：准确版本/提交、下载来源、许可证、FFmpeg configure 选项、MLT configure/CMake 选项、Qt 小版本、Windows MSVC 架构、包前缀与运行时目录、`pkg-config` / `find_package` / 自定义 Find 模块的唯一策略，以及 macOS/Windows 的全新目录验证命令。依赖由用户手动安装；本审计不安装或替代任何依赖。

## 4. 重要缺口（P1）

### P1-1：订阅、设备、验证码与离线状态只有界面边界，没有客户端合同

视觉稿要求三天试用、签名价格目录、订单快照、三设备单活动会话和验证码（视觉清单第 62–66 行）；计划索引只写“客户端入口与签名目录验证和服务调用边界”（第 26–28 行）。缺少价格目录 schema、Ed25519 验签、公钥轮换、版本/有效期/缓存、订单快照、失败 UI、两小时离线状态与“触发云端 AI 时重新检查订阅”的任务和测试。

**修复：** 增设客户端账户与订阅合同任务；后端仍可延期，但客户端不得伪造结果。

### P1-2：资源目录与插件安全的已确认规则没有完整实施合同

资源库要从 Supabase 列表读取一级/二级分类并支持下载状态；插件要由管理员上架、固定 Release 标签、允许旧 Release、Ed25519 验签、独立受限进程。06 计划提到插件宿主与上传队列，但缺少资源目录与插件 manifest schema、旧版本兼容/撤销、哈希校验、安装原子性、插件通信协议和离线表现的明确任务。

**修复：** 在资源/插件模块前先冻结两个独立 schema 与验签测试矩阵；资源下载、安装和升级必须可恢复。

### P1-3：转场范围未被锁定为已确认的三种

用户已确认首版只做“闪黑”“闪白”“叠化”，不进入资源库。00/04 仅泛称“转场”，没有列出类型、参数、RenderGraph 映射、帧边界或测试。

**修复：** 在 00 的模型合同和 04 的 RenderGraph 测试中明确枚举这三种转场，拒绝未知转场。

### P1-4：导出档案仍欠缺可验证的精确定义

07 计划已覆盖 H.264/HEVC、ProRes 4444、硬件优先、质量档和 FFprobe 验证，但没有固化高/中/低的码率/CRF、音频编码与码率、像素格式、帧率继承/转换、HDR 输入转换失败后的行为、文件名冲突策略、硬件失败后的同质量 profile 对等关系。

**修复：** 在导出档案 schema 中逐项固定，并为 macOS VideoToolbox、Windows Media Foundation/NVENC/QSV/AMF、软件 FFmpeg 写能力到 profile 的映射测试。不能以“硬件不可用”降低已选质量语义。

### P1-5：性能门没有量化的冻结基线

08 要生成基准报告，但尚未冻结两台指定机器（Windows i5-10 代/16GB/GTX1030；MacBook Air M1/8GB）的测试素材、版本、采样次数、1080p/4K/轨道数、首帧/拖动/seek/导出指标阈值。仅写“媲美剪映 11.0.0”无法作为可执行验收。

**修复：** 在性能夹具合同中定义受控素材及其 SHA-256、操作脚本、采样方式、阈值、报表字段与与剪映 11.0.0 的可复现实测记录。

### P1-6：视觉清单的自检文字与实际历史覆盖引用相冲突

最终表格 44 个引用均存在；但视觉清单“覆盖与禁止事项”第 73–74 行还列出六个已删除历史 HTML，而第 81 行称“所有指定文件均存在”。若机械扫描所有反引号 HTML，会得到 50 个引用、6 个不存在，造成误报。

**修复：** 修改自检措辞为“页面与最终视觉稿表格内的文件均存在”；历史覆盖文件明确标为不要求存在。不得为了满足检查恢复旧稿。

## 5. 次要缺口（P2）

### P2-1：视觉资产与 QML 设计令牌未建立映射

视觉稿已规定深色密度、青色状态、18×18 图标可见区域、图标外框、标题栏安全区与分栏尺寸，但没有 QML token 文件、SF 图标替代策略、字体回退、最小分辨率/缩放策略、截图阈值定义。若不先冻结，会在不同平台产生视觉漂移。

**修复：** 在 05 之前增加视觉 token/资产合同，并为每个视觉稿状态列出截图基线与允许差异。

## 6. 修复顺序与重新准入标准

1. **先处理 P0-1：** 冻结 QtTest 或 GoogleTest 的唯一选择，并修复全部计划中的测试样例、CMake 与环境文档。
2. **再处理 P0-2：** 建立权威规格与需求追溯矩阵，完成 44 个最终视觉引用和台账决定的逐项映射。
3. **处理 P0-3：** 冻结 macOS/Windows 的依赖版本、构建与发现合同；由开发者按指导安装并在两端验证。
4. **补齐 P1：** 账户/订阅客户端合同、资源与插件 manifest、三种转场、导出档案、性能基准、视觉清单自检语义。
5. **最后处理 P2：** 建立 QML 设计令牌与截图回归阈值。

重新审计的最低准入条件：

- P0 为 0；
- 每个需求 ID 和每个最终视觉状态都能查到一个实施任务与验收编号；
- 任一模块任务可在无旧代码的干净目录中按其文档命令建立、失败、实现、通过；
- 两个平台的依赖发现合同有可复制的成功输出；
- 计划明确不实现的后端能力均有客户端的真实失败/离线界面，不伪造成功。

在上述条件满足前，唯一正确动作是修复方案和计划，不应开始实现 C++、QML、FFmpeg 或 MLT 代码。
